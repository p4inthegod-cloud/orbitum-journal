# ANDROMEDA: вход и оплата

`/login` — пароль, регистрация, ссылка на email, восстановление пароля. После любого способа входа сохраняется безопасный локальный `returnTo`, включая `/pay?plan=lifetime`. Профиль создаёт существующий триггер `handle_new_user`; браузер не пытается записывать отсутствующее поле `profiles.email`.

`/pay` — выбор тарифа и аккаунта → перевод USDT в TON → заявка на ручную проверку. Цены берутся из активных `products`; при ошибке загрузки реквизиты для нового перевода недоступны. Выбор тарифа и черновик сохраняются в sessionStorage отдельно для каждого пользователя. Pending/rejected-заявка восстанавливается из базы. Бессрочный доступ предотвращает ненужную повторную оплату.

## Сервер

`POST /api/notify`, `type: payment_checkout`. Access token проверяется через Supabase Auth. Сервер определяет владельца, проверяет цену и тариф, нормализует Telegram/hash и записывает только pending-заявку. Дубликат возвращает уже существующую заявку. Сбой Telegram не отменяет сохранение и не выдаётся за успешную доставку.

Переменные окружения существующего API:

- `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` — только на сервере.
- `TELEGRAM_BOT_TOKEN` — для уведомления администраторов с привязанным Telegram.
- `APP_URL` — адрес приложения для ссылок в уведомлении.

Адрес TON сохранён из прежней страницы оплаты. Валюта — USDT; TON как валюта оплаты не принимается. Оплата картой и автоматическая проверка блокчейна пока не подключены.

Подтверждение в `/api/admin` вызывает `confirm_andromeda_payment` (EXECUTE только для service_role). Одна транзакция блокирует заявку, активирует доступ и подтверждает платёж. Продление прибавляет 30 дней к ещё действующему сроку; повторное подтверждение не продлевает дважды; lifetime не понижается до monthly.

## Адреса возврата из писем

В Supabase → Authentication → URL Configuration должны быть разрешены точные домены приложения и callback `/login` с query string. Например, для рабочего домена:

```
https://orbitum.trade/login**
https://www.orbitum.trade/login**
```

Для локальной проверки писем можно отдельно добавить `http://127.0.0.1:4173/login**`. Для предпросмотров добавлять только доверенные адреса. Проверить актуальный Site URL и собственный SMTP, не отключая подтверждение email. Существующие callback-адреса других страниц сохранять.

Панель Supabase в браузере требует авторизации; подключённый MCP предоставляет SQL, но не изменение Auth URL Configuration. Реальная доставка письма и allowlist callback пока не подтверждены. Браузерные тесты этих сценариев используют перехват запросов и не отправляют писем.

Документация: [password recovery](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail), [passwordless sign-in](https://supabase.com/docs/guides/auth/auth-email-passwordless), [redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).

## Проверки

```
node --test
```

128 тестов, включая проверки владельца, суммы, inactive-тарифа, повторной заявки, сбоя Telegram и атомарного admin RPC.

`scripts/verify-access.mjs` — изолированный Playwright-сценарий с настоящим локальным SDK Supabase и имитацией внешних API. Нужен сервер `node ../preview-server.mjs`, установленный Playwright (или `PLAYWRIGHT_MODULE` с URL модуля), Chrome (`CHROME_PATH` при необходимости). Проверяет регистрацию, письмо, recovery, вход по Enter, возврат к тарифу, копирование реквизитов, валидацию, восстановление черновика, двойной клик, статусы, ошибки подключения и ширины 320/390/768/1440. Реальные сообщения и платежи не выполняются.

SDK `2.117.2` хранится локально в `js/vendor` с MIT-лицензией: вход не зависит от доступности CDN. Клиент использует публичный publishable key; service key в браузер не передаётся.
